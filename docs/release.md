# Release Process

Harness publishes independently versioned Pi packages from this repository.

## Language

- **Release**: a repository-level delivery event that assigns package versions and makes one or more changed Pi packages available.
- **Publish**: uploading one Pi package version to npm.
- **Releasable change**: a change that affects installed behavior, public metadata, or compatibility of a published Pi package.
- **Release PR**: an automated pull request that applies pending changesets by updating package versions and changelogs before publishing.

## Contributor flow

1. Make the package change.
2. If the change is releasable, add a changeset:

   ```sh
   pnpm changeset
   ```

3. Choose the package-level bump in the changeset:
   - `patch` for compatible fixes or tiny improvements
   - `minor` for new compatible behavior
   - `major` for breaking behavior
4. Open the PR with the code change and changeset.

Changes under `packages/*` should include a changeset unless they are intentionally not releasable. For non-releasable package-area changes, add the `no-release` PR label.

## Release PR flow

A GitHub Actions workflow should create and update a single release PR from `main` when pending changesets exist. The release PR should contain:

- package version bumps
- per-package changelog updates
- removal of consumed changeset files

A maintainer reviews and merges the release PR. Merging the release PR prepares the release; it does not publish packages.

## Publish flow

Publishing is human-triggered and CI-driven.

1. Ensure the release PR has been merged to `main`.
2. Manually trigger the `Publish Packages` GitHub Actions workflow against `main`.
3. The workflow must verify it is running on `main`.
4. The workflow installs dependencies and validates the repo before publishing:

   ```sh
   pnpm install --frozen-lockfile
   pnpm typecheck
   ```

5. If validation passes, the workflow runs:

   ```sh
   pnpm release
   ```

Publishing uses the `NPM_TOKEN` GitHub Actions secret and publishes public `@albizures/*` packages to npm. Changesets creates package-version git tags, such as `@albizures/pi-exit-command@0.1.1`.

One publish trigger publishes the complete ready release set. Maintainers should not manually select individual packages to publish.

## Changelogs

Each published Pi package owns its own changelog in the package directory, generated by Changesets, for example:

```txt
packages/pi-exit-command/CHANGELOG.md
```

The repo does not use one shared root changelog for package history.

## New package publishability checklist

Before a new package is considered publishable, verify that its `package.json` includes:

- `name`
- `version`
- `description`
- `license`
- `publishConfig.access: public`
- Pi metadata pointing to its Pi resources
- appropriate Pi peer dependencies when needed

Also inspect the packed artifact before the first publish, for example:

```sh
pnpm --filter <package> pack --dry-run
```

## Multiple-package releases

Package versions are independent. If one package changes, only that package needs a new version. If multiple packages have pending changesets, they can be released together.

Workspace dependencies between Harness packages must be declared explicitly in `package.json`. Changesets handles dependency version propagation and publish order; maintainers should not hand-maintain publish ordering.

## Failed or partial publishes

Treat publishing as retryable and append-only.

If publishing partially succeeds:

1. Do not unpublish successful package versions.
2. Fix the failure.
3. Re-run the publish workflow from `main`.

The retry should publish remaining unpublished package versions and skip versions already available on npm.

## Pre-releases

Harness does not have a pre-release flow yet. Add alpha, beta, canary, or other npm dist-tag channels only when a real package needs them.
